## 1. 요구사항 분석

기획서는 수강생 기획서 중 유일하게 **개발 착수용 시스템 사양서 수준**(설계 원칙 DP-1~9, 기능 요구 FR-01~27, 화면 C/E/A/K, 데이터 모델, 상태머신, MVP 범위, KPI)으로 작성되어, 별도 해석 없이 원문을 사양서로 사용했다.

- **범위**: MVP-1만 — 정비 Domain, 텍스트 입력, 전체 루프 1회전 (FR 표의 MVP=1 항목)
- **아키텍처**: Phase 1 — 브라우저 + 로컬 JS + **Mock AI Rule Engine** + localStorage. 외부 LLM API 호출 없음(어댑터 인터페이스만 정의)
- **절대 생략 금지 4요소**: `evidence_ref` · 출처 기반 `confidence` · Issue 상태머신 · 회신 루프

핵심 개념은 단순 정보 추출이 아니라 **Dynamic Requirement Identification** — "이 질문을 해결하려면 어떤 정보가 필요한가"를 먼저 판단하고, **전문가의 판단을 바꿀 질문만 최대 3개** 묻는 것이다.

# 2차 고도화 — 현장 입력(음성·이미지·영상) (2026-08-22)

## 1. 배경

기획자(정광호 책임) 현장 적용 피드백: 위험한 현장에서 화면을 보며 텍스트를 입력하는 것은 불편하고 안전 부담 → ①음성 녹음 ②자동 텍스트 변환(STT) ③이미지·영상 첨부(용량 제한) ④멀티모달 AI 분석 ⑤누락 정보 추가 질문 도출을 요청. 원문 사양의 MVP-2(음성)·MVP-3(이미지/영상) 범위를 앞당겨 구현했다.

## 2. 설계 결정

| 결정 | 이유 |
|---|---|
| STT 기본 = Web Speech API, 대안 = Whisper 업로드(사용자 키) | 무료·키 불필요·실시간. 미지원 브라우저/고정밀 필요 시 파일 업로드 전사로 폴백. 키는 localStorage 에만 |
| 타임스탬프는 **세그먼트 단위 자체 기록** | Web Speech 는 타임스탬프 미제공 → 각 final 결과 시각을 녹음 기준 ms 로 기록. 원문 13장 transcript[] {text,start_ms,end_ms} 스키마 그대로라 word-level(로컬 Whisper)로 교체해도 소급 재작업 없음 |
| 미디어 Blob 은 **IndexedDB 전용 스토어**, Issue 에는 media_id 참조만 | localStorage 용량 한계 + DP-1 원본 불변. Phase 2 오브젝트 스토리지 교체 지점 |
| 전사 세그먼트 ↔ 최종 텍스트 **char offset 매핑**(locateSegments) | 사용자가 전사 텍스트를 수정해도 근거 점프 유지. E-02 근거 클릭 → 원문 하이라이트 + 해당 세그먼트부터 오디오 재생 |
| 영상 용량 50MB 설정 상수, 초과 시 즉시 안내 | FR-27 보존 정책과 연동되는 운영 파라미터로 문서화 |
| 비전 분석은 **선택 정밀 모드** (제공사·키 입력 시에만) | 기본 경로는 완전 오프라인 규칙 엔진 유지(Phase 1 제약). 실패해도 기능 저하 없이 안내만 |
| 미디어 분석 → 안전 분기·질문 재산출 연동 | 위험 신호(hazards)는 FR-05 긴급 분기로, 새 단서는 inferred(0.6)로 Gap 반영 후 DecisionImpact 질문 재산출 |
| 녹음 UX = 어두운 오버레이 + 큰 정지 버튼(72px) | 화면 응시 최소화(안전), 장갑 착용 고려 |

## 3. 구현 내역

- `engine/media.js`: 파일 유형/용량 검증, transcript 병합·char 매핑, 프레임 추출 시점 계산 (순수 함수)

- `app/`: C-01 녹음·전사·첨부 UI, C-03/E-02 첨부 표시, E-02 음성 세그먼트 근거 점프, E-03 미디어 분석 섹션, ⚙ 설정(STT 엔진·비전 제공사·키)
- `docs/현장입력_고도화_검토의견.md`: 방식 비교(무료/유료/사내), FR-27 보존 정책, word-timestamp 로드맵, 쉬운 대안, 안전 권고

## 4. 테스트

## 5. 한계 / 남은 결정

- Web Speech 는 크롬/엣지 + 네트워크 필요(음성이 브라우저 제조사 서버 경유) — 사내 보안 검토 필요, Phase 2 로컬 STT 가 최종 답

## 2026-08-25 — 실제 운영 가능한 사이트로 (서버 모드 · 계정 · 상태 정합)

### 한 일

1. **상단 메뉴 오른쪽 정렬** — `.topbar-inner` 로 감싸고 `space-between`.
2. **앱과 DB 의 상태 불일치 해소** — 상태 목록·전이표를 `engine/statemachine.js` 에서 굽는다.
3. **서버 저장 + 로그인** — `app/fi-supabase.js` 신설, `Store` 인터페이스 유지.
4. **문서** — README 5-1 절, `SUPABASE-설정.md` 갱신.

### 왜 (사고가 될 뻔한 것)

**연결했으면 첫 접수부터 죽었을 상태였다.**
화면은 12개 상태(`DRAFT·SUBMITTED·ASSIGNED·IN_REVIEW·PENDING_FIELD·ANSWERED·
RESOLVED·REOPENED·KNOWLEDGE_READY·MERGED·STALE·CLOSED_UNVERIFIED`)로 도는데,
`supabase/schema.sql` 의 check 제약은 화면에 없는 이름 6개
(`CONCLUDED`·`REPLIED`·`CLOSED`)를 포함한 6개만 허용하고 있었다.
스키마를 기획서 보고 손으로 적고, 구현은 따로 갔기 때문이다.

`tsc` 도 `vite build` 도 SQL 을 봐 주지 않고, 화면에는 "저장이 안 된다"로만 보인다.
그래서 **두 곳에 손으로 적는 것을 그만두고 한쪽에서 굽기로** 했다
(`tools/build-sql-states.js`). 어긋나면 `--check` 와 단위 테스트가 죽는다.

### 상단 메뉴가 왼쪽에 몰려 있던 진짜 이유

`header.topbar h1 { margin-right: auto }` 는 멀쩡히 적혀 있었는데 죽어 있었다.
공통 테마의 `.hd.hd-app :where(h1, …) { margin: 0 0 .5em }` 이
**단축 속성**이라 오른쪽 마진까지 0 으로 되돌렸고,
특정도가 (0,2,0) 대 (0,1,2) 라 테마가 이겼다.
`:where()` 는 자기 특정도가 0 이지만 **앞의 `.hd.hd-app` 두 클래스는 그대로 센다** — 이걸 놓쳤다.
이제는 auto 마진에 기대지 않고 `justify-content: space-between` 으로 세운다.
마진이 다시 덮여도 배치가 무너지지 않는다.

### 저장 순서를 지켜야 하는 이유

관문이 실제로 지켜지려면 **① 이슈 행 → ② 결론·회신·해결확인 → ③ 상태 올리기** 순서라야 한다.
반대로 하면 "결론이 없으면 ANSWERED 로 갈 수 없습니다" 로 막힌다.
그리고 관문을 `INSERT` 에도 걸었다 — `UPDATE` 에만 걸면
**처음부터 `ANSWERED` 로 만들어 넣는** 길이 열려 결론도 회신도 없는 "답변 완료" 가 생긴다.

### 2026-08-25 (이어서) — 정말 도는지 증명하기

말로 "된다"고 적는 대신 **증명 가능한 형태**로 바꿨다.

**`scripts/sqltest/run-server-test.sh`** — 임시 PostgreSQL 에 진짜 `schema.sql` 을 올리고,
**고치지 않은 `app/fi-supabase.js` 를 그대로** 태워 한 바퀴 돌린다.
supabase-js 자리에는 psql 로 말을 옮기는 가짜 클라이언트를 끼웠다.

단위 테스트는 어댑터의 계산만, SQL 하네스는 DB 규칙만 본다.
**둘이 맞물리는 지점은 아무도 안 보고 있었다** — 컬럼 이름·저장 순서·상태 경로·첨부 업로드.

여기서 실제로 잡힌 것 두 가지.

1. **`attachment` 표에 유니크 제약이 없었다.** upsert 가 기댈 것이 없으니 같은 첨부를
   다시 저장할 때마다 행이 쌓인다(§3.7 의 그 함정 그대로). 제약을 넣고,
   `create table if not exists` 로는 기존 표에 안 붙으므로 `alter table` 보정도 함께 넣었다.
2. **부분 전이가 일어난다.** `ASSIGNED → ANSWERED` 를 시도하면 `IN_REVIEW` 까지는 통과하고
   거기서 막힌다. 해롭지 않다 — 중간 상태도 정당하고, 다음에 읽을 때 컬럼 값으로
   화면이 스스로 맞는다. 다만 **structured 안에는 올리려던 값이 남으므로**
   그것을 믿으면 화면이 "답변 완료"로 보인다. 상태의 정본은 컬럼이라는 규칙이
   여기서 실제로 필요하다는 것이 드러났다.

**첨부 미디어를 서버로 옮겼다.** 비공개 버킷 + 한 시간짜리 서명 주소.
이 기기에 원본이 없으면(남이 올린 것) 서버에서 받아 온다 — 이 갈래가 없으면
전문가 화면에서 현장 사진이 통째로 비어 보인다.
지우는 정책은 두지 않았다. 원본은 판단의 근거라 화면에서 지울 수 있으면 안 된다.

**깨뜨리기 확인 (통합 5종)**
저장 순서 뒤집기 / structured 의 상태를 믿기 / 변경 판정 없애기 /
경로 정리 없애기 / `voice`→`audio` 변환 없애기 → 다섯 경우 모두 테스트가 잡았다.

두 번째 것은 처음에 **안 잡혔다.** 컬럼과 structured 가 어긋난 건이 검사에 없었기 때문이다.
관문에 막혀 상태가 안 올라간 이슈(#2002)를 쓰니 그제야 잡혔다 —
**검사가 성립하려면 둘이 실제로 어긋나 있어야 한다**는 단정문도 함께 넣었다.
다섯 번째도 처음엔 안 잡혔다. 앱이 `kind` 에 `voice` 를 넣지 않아 방어 경로가
안 밟혔던 것이라, `voice` 가 들어오는 검사를 따로 만들었다.

**남은 것**: 서버 모드 E2E(Playwright)는 계정이 있어야 해서 아직 없다.
통합 테스트가 그 자리를 대신하고 있다.

### 2026-08-25 (이어서) — 상단 바 고정 · 첨부 흐름 개선

**상단 바가 안 붙어 있었다.** `header.topbar` 는 `position: sticky; top:0` 인데
스크롤하면 그대로 밀려 올라갔다(실측 −463px).
공통 테마의 `html, body { overflow-x: hidden }` 때문이다 — 한 축이 visible 이 아니면
다른 축이 auto 로 계산되어 **스크롤 컨테이너**가 되고, sticky 는 뷰포트가 아니라
그 컨테이너를 기준으로 붙는다. 가로 넘침을 막는 규칙이라 걷어낼 수 없으므로
**fixed** 로 못 박았다. (hd-project05 도 같은 원인이었다)

높이는 `syncChrome()` 이 **실측해서** CSS 변수로 넣는다.
숫자로 박으면 띠 문구가 길어져 두 줄·세 줄이 되는 순간 어긋난다 —
390px 에서 실제로 세 줄(202px)이 된다.

**첨부 흐름**
- 사진·영상을 **끌어다 놓을 수 있게** 했다. 버튼은 남겼다 — 휴대폰에서는
  끌어다 놓기가 안 되고 카메라를 바로 여는 편이 낫다.
- **여러 장을 한 번에** 넣는다. 한 장씩만 받으면 현장에서 몇 번을 반복해야 한다.
- 끌어다 놓기는 요소가 아니라 **root 에 위임**해 걸었다. 화면을 다시 그릴 때마다
  요소가 새로 생기므로, 요소마다 걸면 다시 그린 뒤 조용히 동작하지 않는다.
- 첨부 영역 **밖**에 떨어뜨리면 브라우저가 그 파일을 열어 입력하던 내용이 날아간다.
  바깥에서는 아무 일도 없게 막았다.

**API 키 상태를 첨부하는 자리에서 보여 준다.**
설정 화면까지 들어가야 알 수 있으면 아무도 확인하지 않는다 —
키 없이 사진을 올려 놓고 "왜 분석이 안 되지" 하게 된다.
꺼져 있어도 접수는 그대로 된다(오프라인 규칙 엔진). 그 사실도 함께 적는다.
